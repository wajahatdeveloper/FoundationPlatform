# Messaging (EventBus) — Architecture Audit

## Context

Scope audited (every `.cs` file read in full):
- `Packages/com.aethernexus.foundationplatform/Runtime/Messaging/EventBus/` — `EventBus.cs`, `BaseGameEvent.cs`, `BaseValidatableEvent.cs`, `BroadcastGlobalAttribute.cs`, `DomainEvent.cs`, `EventChannelAttribute.cs`, `EventDataAttribute.cs`, `EventDebugScope.cs`, `Events.cs`, `IEntitySpawnState.cs`, `IEventDebugSignalEmitter.cs`, `IIdentity.cs`, `Identity.cs`, `NoSubscriberBehaviorAttribute.cs`, `SubscriptionToken.cs`.
- `Packages/com.aethernexus.foundationplatform/Editor/Messaging/EventBus/` — `ActiveSubscriptionsWindow.cs`, `EventBusConstants.cs`, `EventBusEditorWindowRefresh.cs`, `EventBusModels.cs`, `EventBusSharedState.cs`, `EventBusTabControllers.cs`, `EventBusToolbars.cs`, `EventBusUtilities.cs`, `EventBusWindow.cs`, `EventChannelGenerator.cs`, `EventPublishHistoryWindow.cs`, `SimpleEditorTableView.cs`, `SubscriptionHistoryWindow.cs`.

Checked against `docs/00-AgentGuide.md`, `docs/01-CorePrinciples.md`, `docs/02-Libraries.md`, `docs/09-EditorHub.md`, `docs/13-AuthoringStandards.md`, `docs/11-Determinism.md`, and this package's `Documentation~/ARCHITECTURE.md`.

`EventBus` is a single static class (`AetherNexus.FoundationPlatform.Messaging.EventBus`) providing typed pub/sub with per-channel (`Identity`) subscriber lists, priority ordering, a `DomainEvent` publish gate, optional monitoring/history (editor/dev-build only), and an optional `IEventDebugSignalEmitter` hook that GameEngineCore registers at bootstrap. Editor tooling is a tabbed "Event Bus" hub window (Publish History / Active Subscriptions / Subscription History) plus a small C# class-file generator.

## Findings

### Execution Spine
No findings. `EventBus` is notification-only: `PublishInternal` only invokes subscriber delegates, it never touches simulation state itself. The `DomainEvent` gate (`EventBus.cs:116-155`, enforced at `EventBus.cs:1298-1309`) actively enforces the docs/02 contract — publishing a `DomainEvent` outside `BeginDomainPublishGate`/restoration mode throws (`InvalidOperationException`) rather than silently succeeding, which correctly prevents the bus from becoming a second mutation path. This matches docs/01's "no side doors" and docs/11's replay/restoration model.

### Data/Controller/View Boundary
No findings specific to this folder — `EventBus` and its editor tooling are pure infrastructure with no Data/Controller/View role of their own. (The one questionable "Data"-shaped type living here, `IEntitySpawnState`, is reported under Redundancy/Simplification below since the more actionable problem is that it is dead code in the wrong layer, not a spine violation.)

### Ownership
No findings. Exactly one bus: `EventBus` is `static`, subscriber storage is a single `Dictionary<Type, Dictionary<Identity, List<PrioritizedCallback>>>` (`EventBus.cs:29`). `EventBusSharedState` (Editor/Messaging/EventBus/EventBusSharedState.cs:8-21) is a lazily-created plain singleton scoped to editor tooling only, and it explicitly detaches itself on `beforeAssemblyReload` (`EventBusSharedState.cs:23-40`) instead of leaking stale handlers across domain reload — correct pattern, mirrors the `IdentityComponent` reset convention referenced in its own comment.

### Designer Surface Priority
- **Warning** — `EventPublishHistoryWindow.SettingsModel.AddRuleSystemDefine()` (`Editor/Messaging/EventBus/EventPublishHistoryWindow.cs:143-175`) is a button inside the EventBus debug window's Settings panel that calls `PlayerSettings.SetScriptingDefineSymbols` for the active build-target group, adding `RULESYSTEM_PRESENT` project-wide. A foundation-layer diagnostic window mutating a *global, project-wide, cross-package* build setting from a debug panel is a step beyond what docs/09/13 mean by "debug/power tools" as the editor-window last resort — this isn't validating or inspecting the EventBus, it's silently reconfiguring the whole project's compile symbols for every assembly, gated behind a button whose label ("Add RULESYSTEM_PRESENT Define") gives no indication of that project-wide blast radius. This kind of build-configuration change belongs to project/build settings tooling (or the owning package's own onboarding), not a Foundation Platform message-bus debug hub.
- **Info** — `EventChannelGenerator` (`Editor/Messaging/EventBus/EventChannelGenerator.cs`) is a bespoke `EditorWindow` for authoring a new event source file. Per docs/13 "Extension pattern," a new authored-type creation flow should prefer Project/Hierarchy/Inspector entry points; this one is defensible as scaffolding (it's generating raw `.cs`, not a mapped ScriptableObject asset the Project window model covers), but see the Doc/Architecture Drift finding below — its own UI text overpromises what it does.

### Redundancy/Simplification
- **Warning** — `IEntitySpawnState.cs` (`Runtime/Messaging/EventBus/IEntitySpawnState.cs:1-12`) defines `NextUnitSpawnIndex`/`NextCitySpawnIndex` — product-specific domain vocabulary ("unit", "city") — inside FoundationPlatform's genre-agnostic Messaging folder. A repo-wide search found **zero usages** anywhere outside this one file. This is both dead code and a domain-content leak into the base layer that docs/02 explicitly forbids owning ("Product-specific domain content or shipping game assets"). Delete it, or if it's still needed, move it to the package that actually owns spawn-index bookkeeping (GameEngineCore or the tactical layer).
- **Info** — `BaseValidatableEvent.cs` (`Runtime/Messaging/EventBus/BaseValidatableEvent.cs:8-18`) — `IsValidated`/`ValidationMessage` on a `BaseGameEvent` subclass — has zero usages anywhere in the repo. Dead code; also a latent footgun if ever adopted, since round-tripping "is this valid" through an event object invites treating the bus as a synchronous validation-return channel, which is exactly the anti-pattern docs/01/02 warn against (validation belongs in the action pipeline's `Validate` phase, not an event property).
- **Info** — `EventBusToolbars.cs` (`HistoryTabToolbar`, `SubscribersTabToolbar`, `SubscriptionsTabToolbar`, ~300 lines) and `EventBusTabControllers.cs` (`HistoryTabController`, `SubscribersTabController`, `SubscriptionsTabController`, ~700 lines) are three near-identical implementations of the same search/sort/filter/cache-invalidation pattern, differing only in field names and the sort-by enum. Pure editor tooling, no behavioral risk, but a large amount of copy-pasted logic that a shared generic base (`TabToolbar<TSortBy>` / `TabController<TRow, TSortBy>`) would collapse significantly.
- **Info** — `EventBus.cs` carries roughly 450 lines (`EventBus.cs:258-717`, `RULESYSTEM_PRESENT`-gated) of reflection-based heuristics (`IsRuleSystemClass`, `GetActualClassName`, `ExtractRuleMethodName`) whose sole purpose is to make the debug history/subscriber windows display GameEngineCore's `RuleHandler`/`GameAction` naming nicely. It hardcodes ~15 GameEngineCore class names by string (`EventBus.cs:271-287`: `GameActionPipeline`, `RuleRegistry`, `ValidationContext`, `RuleDebug`, `RulePriority`, `RuleCategories`, `RuleFeature`, `IRuleAction`, `GameActionCommitted`, `GameActionValidationEvent`, `GameActionException`, `RulesBootstrap`, `RuleSetSubscriptionHelper`, `StandaloneRuleSet`, `AsyncFlowVisualizerWindow`, plus `RuleSetBehaviour`). This is diagnostic-only (editor/dev-build) and doesn't create a hard assembly reference, but it is a large amount of complexity in the foundation layer's core runtime file dedicated to cosmetics for one specific downstream package — see the matching Doc/Architecture Drift finding below for the layering concern.

### Determinism
No findings. Subscriber ordering is deterministic: `SubscribeInternal` inserts by priority with a stable tie-break that preserves insertion order for equal priorities (`EventBus.cs:1016-1023`), so identical subscribe-then-publish sequences reproduce identical dispatch order, matching docs/11 ("same subscribe order and publish sequence for the same action stream"). No `UnityEngine.Random` anywhere in this scope. `DateTime.Now` (`BaseGameEvent.cs:40`) and `UnityEngine.Time.frameCount` (`EventBus.cs:759`) are used exclusively for editor/dev-build diagnostic provenance (`#if UNITY_EDITOR || DEVELOPMENT_BUILD`) and never influence which subscribers run or in what order — they annotate history entries only, so they don't violate the "no wall-clock/frame-timing in simulation" rule.

### Doc/Architecture Drift
- **Warning** — `Documentation~/ARCHITECTURE.md`'s "Event Bus" section (lines 49-72) describes `EventBus` as a clean, standalone pub/sub with `[BroadcastGlobal]`, the domain publish gate, `Identity` channels, and `SubscriptionToken` — accurate as far as it goes, but omits that the runtime file also hardcodes ~15 GameEngineCore class names for cosmetic debug-display purposes (`RULESYSTEM_PRESENT`, see Redundancy finding above), and omits the `AddRuleSystemDefine()` PlayerSettings-mutating button in the Editor tooling. A reader of ARCHITECTURE.md would reasonably conclude FoundationPlatform's EventBus has zero knowledge of upstream packages; that's not the case for its debug-display path. Worth a short note in ARCHITECTURE.md (or moving the coupling behind the existing `IEventDebugSignalEmitter`-style seam, which is the pattern the file already correctly documents and which GameEngineCore correctly implements/registers rather than FoundationPlatform reaching upward).
- **Info** — The header comment in `Events.cs:6-9` tells readers "To create EventChannel ScriptableObjects for these, use: Tools → EventBus → Generate Event Channel." Neither claim matches the codebase: (1) the actual menu path is `Window/Utilities/Create Event Channel...` (`Runtime/Menus/MenuPaths.cs:90`, under `MenuPriorities.WindowUtilities`), not `Tools → EventBus`; (2) `EventChannelGenerator.GenerateEventChannel()` (`Editor/Messaging/EventBus/EventChannelGenerator.cs:129-175`) writes a plain `BaseGameEvent`-derived `.cs` file — no ScriptableObject, no `CreateAssetMenu` — so there is no "EventChannel ScriptableObject" being created. The tool's own `_menuPath` field (`EventChannelGenerator.cs:12`) is captured from the UI and echoed back in the success dialog (`EventChannelGenerator.cs:173`) but is never written into the generated code or any asset-menu attribute — it does nothing.

### Codebase Gotchas
No findings on the specific §3 traps: no `??` on a `UnityEngine.Object` anywhere in this scope (Unity-object null checks are used correctly, e.g. `EventBusModels.cs:54` `_ownerWindow == null`); no struct instance-field initializers (`Identity`, `SubscriptionToken`, `EventDebugScope` all assign fields via constructor only); no `OnValidate`/`OnAfterDeserialize` writes (no MonoBehaviour/ScriptableObject in this scope); the `GameEngineCore.Debug` namespace collision doesn't apply (this code lives under `AetherNexus.FoundationPlatform.*`). Editor windows correctly pair subscribe/unsubscribe in `OnEnable`/`OnDisable` with explicit re-entrancy guards (`_enabledGuard` in `EventPublishHistoryWindow.cs:209`, `SubscriptionHistoryWindow.cs:95`, `ActiveSubscriptionsWindow.cs:104`), and `ActiveSubscriptionsWindow` additionally guards against one instance clearing another live instance's shared static delegate (`ActiveSubscriptionsWindow.cs:142-146`) — a genuinely careful pattern, not a gotcha.

- **Info** — `EventBus.cs`'s reflection-heavy debug-metadata code (`SerializeEventData`, `GetActualClassName`, `ExtractRuleMethodName`, property/attribute lookups) is guarded by `#if UNITY_EDITOR || DEVELOPMENT_BUILD`, not `#if UNITY_EDITOR` alone. `DEVELOPMENT_BUILD` is a real player/device build configuration (e.g. a development build deployed to a console or mobile device), not "editor tools" — the project's stated policy is "No runtime reflection (AOT target) — reflection only in editor tools." The reflection used here (property/attribute lookups, no `Reflection.Emit`/dynamic codegen) generally works under IL2CPP/AOT, so this is unlikely to break builds, but it is reflection compiled into non-editor player code, which is worth a conscious confirmation from whoever owns the `DEVELOPMENT_BUILD` diagnostic scope rather than a silent assumption.

## Fixes

No source files were modified — findings only, per audit scope (only `AUDIT.md` may be written). Suggested follow-ups, roughly in priority order:

1. Delete unused `Runtime/Messaging/EventBus/IEntitySpawnState.cs` and `Runtime/Messaging/EventBus/BaseValidatableEvent.cs`, or relocate `IEntitySpawnState` to the package that actually owns unit/city spawn-index bookkeeping.
2. Move `AddRuleSystemDefine()`/`HasRuleSystemDefine()` out of the EventBus debug window (or remove them) — a project-wide Scripting Define Symbols mutation shouldn't live behind a button in a message-bus diagnostic panel.
3. Route GameEngineCore-specific debug-display knowledge (the `RULESYSTEM_PRESENT` class-name list and rule-name extraction in `EventBus.cs`) through an optional registered adapter instead of hardcoded class-name strings in the Foundation layer, mirroring the `IEventDebugSignalEmitter` seam this same file already uses correctly for telemetry.
4. Fix the `Events.cs` header comment to reference the real menu path (`Window/Utilities/Create Event Channel...`) and either remove `EventChannelGenerator`'s unused `_menuPath` field or make it do something (e.g. emit a `[CreateAssetMenu]`-bearing companion asset if that was the original intent).
5. Optionally collapse the three near-duplicate toolbar/tab-controller trios in `EventBusToolbars.cs`/`EventBusTabControllers.cs` behind a shared generic base to cut ~1000 combined lines of repeated logic.
6. Confirm whether the reflection-based debug-metadata path in `EventBus.cs` is intended to compile into `DEVELOPMENT_BUILD` player builds (device dev-build debugging) or should be tightened to `UNITY_EDITOR` only.
