# CoroutineX — Architecture Audit (Vendored Framework)

## Context

`CoroutineX` is listed in `docs/00-AgentGuide.md` §4 ("Vendored & generated code — do not hand-edit") as a **vendored framework**, alongside RagdollHelper and IndicatorPackage/OffScreenIndicator. Per that doc: *"To 'fix' vendored code: revert to upstream and apply the change as configuration or a wrapper, not an in-place patch."*

This changes the audit's shape versus a normal first-party subsystem review:

- The primary question is not "is this code well-designed" but **"has this vendor file been hand-patched in place, and is that patching now indistinguishable from the vendor baseline because nobody diffs against upstream?"**
- Findings that would be routine "simplify this" suggestions for first-party code (e.g. odd async additions, dead code) are instead treated as **vendor-integrity evidence** — signs the file diverged from a clean upstream drop.
- No upstream source tree for CoroutineX was available to this audit (no `upstream/`, `vendor-lock`, or version-pinned copy found alongside the package, and no internet fetch was performed). All "hand-patch" conclusions below are inferred from **internal evidence** — style breaks, project-specific coupling, leftover dead code — not a line-by-line diff against a verified upstream release. This is stated as a limitation, not a hedge: a real diff against upstream should be done before deciding how to remediate.
- Scope read in full (10 `.cs` files): `Runtime/CoroutineX/CoroutineX.cs`, `Runtime/CoroutineX/Components/{CoroutineXExecutor,CoroutineXGroup,CoroutineXOwner,EnumerableEnumerator,Routines}.cs`, `Runtime/CoroutineX/SubScripts/{CoroutineXExtensions,WaitForAll,WaitForAny,YieldAwaiter}.cs`, `Editor/CoroutineX/CoroutineXOwnerEditor.cs`.

## Findings

### Vendor Integrity

**[Warning]** `CoroutineX.cs` has project-specific structured-logging calls woven directly into vendor control flow, not just a namespace rename.
- File: `Runtime/CoroutineX/CoroutineX.cs`, lines 13 (`using AetherNexus.FoundationPlatform.DebugX;`), 199, 549, 557, 563, 572, 665 (`DebugX.Logger(LogChannels.DevTools).Error(...)` calls inside `CurrentState` setter, `Run()`, `SetOwner()`).
- Why it matters: renaming a vendor file into the project's namespace convention is normal, low-risk vendoring practice. Wiring the file's error paths to the **project's own logging framework** (`AetherNexus.FoundationPlatform.DebugX`, itself a sibling first-party library in this same package) is a functional modification of vendor behavior — the original vendor almost certainly used `Debug.LogError` or threw, not a project-specific structured logger with named channels (`LogChannels.DevTools`). Every future upstream re-pull will conflict here, and there is no wrapper/config layer isolating this from the vendor file itself — it is an in-place patch of exactly the kind §4 says not to do. (It may well be a deliberate, sanctioned integration seam rather than an accidental patch — see Fixes.)

**[Warning]** A ~50-line block of dead, commented-out legacy code sits at the bottom of the vendor file.
- File: `Runtime/CoroutineX/CoroutineX.cs`, lines 861–908 — a full, different, static-class implementation of `CoroutineX` (`private static CoroutineOwner CoroutineOwner`, `StartCoroutine(this IEnumerator)`, `internal class CoroutineOwner : MonoBehaviour`), left commented out after the real (instance-based) `CoroutineX` class closes.
- Why it matters: this is not upstream vendor style (shipped vendor packages don't ship a dead alternate implementation of the same type commented out beneath the real one). It is residue of an in-place rewrite done directly in this file — someone replaced a static-facade `CoroutineX` with the current instance/state-machine design and left the old code as a comment instead of deleting it or re-vendoring cleanly. It is itself evidence for the same conclusion as the finding above: this file has been directly edited, not treated as a locked vendor drop.

**[Info]** `WaitForCompletionAsync`, `RunAsync<T>`, `RunAsync` use raw `System.Threading.Tasks.Task`, stylistically foreign to the rest of the file.
- File: `Runtime/CoroutineX/CoroutineX.cs`, lines 826–857.
- Why it matters: every other member in the class is expressed in the coroutine/event/awaiter idiom (`YieldAwaiter`, `Action<CoroutineX>` events, `IEnumerator`-driven state machine). These three methods are the only ones using `async`/`Task`, and `RunAsync` in particular (`Task.Run(function)` / `Task.Run(action)`) has nothing to do with `CoroutineX` at all — it does not touch `_enumerator`, `_coroutine`, or any instance state; it is a generic thread-pool helper bolted onto an unrelated class. Combined with the fact that this package **already embeds UniTask** (`Runtime/ThirdParty/UniTask/`) as its async primitive elsewhere, adding a third ad-hoc raw-`Task` surface here reads as an unreviewed local addition rather than vendor content. Low severity because it's inert/additive (doesn't change existing behavior), but it's more evidence the file is not a clean vendor copy.

**No findings** beyond the above for the other 9 files (`CoroutineXExecutor`, `CoroutineXGroup`, `CoroutineXOwner`, `EnumerableEnumerator`, `Routines`, `CoroutineXExtensions`, `WaitForAll`, `WaitForAny`, `YieldAwaiter`, and the Editor custom inspector). These read as internally consistent, uniform in style, free of TODO/FIXME/HACK markers, and contain no other project-specific couplings (grepped for `TODO|FIXME|HACK|XXX` across the whole folder — the only matches were namespace declarations). The namespace rename to `AetherNexus.FoundationPlatform.CoroutineX` is applied uniformly across all 10 files and is treated here as ordinary vendoring, not a patch.

### Ownership

**No findings** of a second/competing coroutine helper inside the audited package or in the `GameFramework` packages checked. Search for `class *Coroutine*(Manager|Runner|Helper|Utility|Pool)` across `Packages/` returned nothing.

**[Info]** Downstream availability is confirmed via `global using`, but no gameplay call sites were found in this scope.
- Evidence: `QuestSystem`, `ItemSystem`, `CharacterSystem` (all under `com.aethernexus.gameframework`) and `CharacterSystem/Editor/RagdollHelper` each carry `global using AetherNexus.FoundationPlatform.CoroutineX;` (and `RagdollHelper` additionally pulls in `AetherNexus.FoundationPlatform.Editor.CoroutineX`). This confirms CoroutineX is the intended shared coroutine utility reachable from those packages.
- However, a repo-wide grep for actual call sites (`CoroutineX.Run(`, `CoroutineX.Create(`) inside `Packages/` found matches only in: `FoundationPlatform/Runtime/Extensions/Scene/SceneManagerX.cs` (scene load/unload — lifecycle, not gameplay simulation), the package's own `SubScripts/CoroutineXExtensions.cs`, and the `Samples~/EventBusCoroutineDemo` sample/README. No actual invocation was found inside QuestSystem/ItemSystem/CharacterSystem/RagdollHelper runtime code despite the `global using` — meaning either (a) those packages don't currently call it despite importing it, or (b) usage exists under a different call pattern (e.g. via `Routines.*`, extension methods, or an alias) not caught by this grep.
- This is a genuine limitation of a folder-scoped audit: cannot fully confirm "ownership" without inspecting the consuming packages' logic, which are separately scheduled (GameEngineCore, GameFramework, TacticalFeatures audits). Flagged as a cross-reference, not asserted as fact.

**[Info]** `UniTask` (embedded third-party, `Runtime/ThirdParty/UniTask/`) and `CoroutineX` are two separate vendored async/deferred-execution mechanisms co-resident in the same base package. Not a "competing coroutine helper" in the sense the task asked about (different paradigm: `Task`-like vs Unity coroutine), but it is a second vendored async substrate in the same layer, and CoroutineX's own `RunAsync`/`WaitForCompletionAsync` additions (see Vendor Integrity) blur the line further by adding a *third*, ad-hoc `Task`-based path. Worth a consolidation conversation at the platform level; not a defect in this folder by itself.

### Determinism

**No findings** of CoroutineX being used for gameplay-affecting delays within the audited scope.
- `Routines.Delay(float, ...)` (`Runtime/CoroutineX/Components/Routines.cs`, lines 19–39) uses `UnityEngine.WaitForSeconds` and `Routines.FrameDelay` waits on frame counts — both are frame/wall-clock timing, which docs/11 and docs/00 §3 forbid for **simulation** timing but explicitly allow for **presentation** timing. Nothing in this folder self-identifies as a simulation/gameplay-rule path; `Routines` is documented as "auxiliary class for regular coroutine tasks," consistent with a presentation-only utility.
- The one confirmed real caller found in this audit, `SceneManagerX` (`FoundationPlatform/Runtime/Extensions/Scene/SceneManagerX.cs`), uses `CoroutineX.Run(...)` for async scene load/unload sequencing — lifecycle/presentation-adjacent, not authoritative simulation state.
- **Limitation** (as anticipated by the task): this audit cannot see inside `GameFramework`, `GameEngineCore`, `GameplayAbilitySystem`, or `TacticalFeatures` call sites. The `global using` imports noted under Ownership mean those packages *can* reach `CoroutineX`/`Routines.Delay` for a gameplay effect timer without it being visible from this folder. This should be explicitly checked when those packages are audited (tasks already queued): grep those packages for `CoroutineX.Run(`, `Routines.Delay(`, `Routines.FrameDelay(` and confirm none feed a gameplay-rule outcome (health, damage timing, resource grants, etc.) — if any do, that is a docs/11 violation ("New delayed gameplay effect: scheduler with explicit ordering, not coroutine frame waits without contract"), not a CoroutineX defect per se.

### Redundancy/Simplification

**No findings** of non-vendor wrapper code doing something odd, unused, or duplicative within this folder. The one non-Runtime file in scope, `Editor/CoroutineX/CoroutineXOwnerEditor.cs`, is a small `CustomEditor(typeof(CoroutineXOwner))` debug list view (index/name/state/last-result columns for active coroutines on a GameObject). It is gated correctly behind `#if UNITY_EDITOR`, does one thing, and is not duplicated elsewhere in the folder.
- The (Warning-level, additive) `RunAsync`/`WaitForCompletionAsync` methods noted under Vendor Integrity are the closest thing to "odd/unused" code in this scope, but they are reported there since their significance is as vendor-drift evidence, not as ordinary dead weight.

### Doc/Architecture Drift

**[Warning]** The package's own `Documentation~/ARCHITECTURE.md` documents CoroutineX as ordinary first-party FoundationPlatform infrastructure and never states it is vendored.
- File: `Packages/com.aethernexus.foundationplatform/Documentation~/ARCHITECTURE.md`, line 5 ("Provides: EventBus, DebugX, CoroutineX, TweenX, patterns, ...") and the dedicated `## CoroutineX` section, lines 108–125, which documents the public API (`Run`, `Stop`, `Reset`, `Rerun`, `SetOwner`/`MakeUnowned`, `WaitForComplete`/`WaitForStop`/`WaitForRun`/`WaitForReset`, state events) exactly like any other in-house component (`EventBus`, `DebugX`, `Patterns`) — with no callout that it is vendored, no "do not hand-edit" note, and no pointer back to `docs/00-AgentGuide.md` §4.
- Why it matters: per `docs/00-AgentGuide.md` "Where things live," the package's own `ARCHITECTURE.md` is exactly the doc a programmer or agent is expected to consult for "symbol-level detail" when working in this package (see also `docs/03-Frameworks.md`'s per-package pointer). Someone following the documented path (`03-Frameworks.md` → package `ARCHITECTURE.md`) never encounters the vendored/do-not-hand-edit status at all — only `docs/00-AgentGuide.md` §4 records it, in one line, in a table of examples. That is a single point of documentation for a rule whose violation is explicitly called out as a defect ("Changing these by hand is a defect even if it compiles"). This is exactly the kind of gap that would let a future well-intentioned contributor open `CoroutineX.cs`, see clean-looking first-party-style code (matching the rest of the package's namespace and doc conventions), and patch it in place — which per the Vendor Integrity findings above may already have happened once.
- Same gap repeats at two more doc layers, confirming it's not a one-off oversight: `docs/03-Frameworks.md` line 77 and `Assets/Docs/ARCHITECTURE.md` line 29 both list CoroutineX alongside EventBus/DebugX/TweenX/etc. under "Base platform layer" with no vendored annotation.

## Fixes

These are recommendations only — no source file other than this `AUDIT.md` was modified, per instructions.

1. **Diff against real upstream before touching `CoroutineX.cs` further.** Locate (or re-download) the actual upstream CoroutineX source this was vendored from, and do a real line diff against the current `Runtime/CoroutineX/CoroutineX.cs`. This audit's "hand-patch" conclusions are inferred from internal style evidence, not a verified diff — do that diff before deciding what "revert to upstream" means concretely here.
2. **Decide, deliberately, whether the DebugX coupling is a sanctioned integration seam or an accidental patch.** If the team wants CoroutineX's error paths to go through `DebugX` permanently, that is a legitimate configuration choice — but it should be recorded as such (e.g. a short note in the package `ARCHITECTURE.md` under CoroutineX: "error logging intentionally routed through DebugX; this is the one accepted deviation from upstream"), rather than left to be discovered as an undocumented in-place patch. If it is *not* intentional, revert to upstream's original error handling and reintroduce logging via an external hook (e.g. an injected `Action<string>` or an event subscription from a first-party wrapper file outside `CoroutineX.cs`) instead of a hard `using AetherNexus.FoundationPlatform.DebugX` inside the vendor file.
3. **Delete the dead commented-out block** (`CoroutineX.cs` lines 861–908) once step 1's diff confirms it isn't present in upstream (it almost certainly isn't — it's a different implementation of the same type). Dead-code removal is hygiene, not a behavior patch, but should still happen as part of a deliberate re-vendor/cleanup pass rather than an ad-hoc edit, so it doesn't silently reset any other in-place changes at the same time.
4. **Add the vendored/do-not-hand-edit callout to `Documentation~/ARCHITECTURE.md`.** A one- or two-line note at the top of the `## CoroutineX` section ("Vendored framework — see `docs/00-AgentGuide.md` §4; do not hand-patch, revert to upstream + wrapper instead") would close the doc-drift gap and is explicitly sanctioned by `docs/00-AgentGuide.md` §2 ("Docs freshness … update the matching … package's `ARCHITECTURE.md` … in the same task"). Consider the same one-line annotation in `docs/03-Frameworks.md` and `Assets/Docs/ARCHITECTURE.md` where CoroutineX is listed, so the status is visible wherever it's referenced, not only in the AgentGuide's vendored-code table.
5. **No action recommended** for the UniTask/CoroutineX co-existence or the `RunAsync` additions beyond what's already flagged — these are platform-level design questions (does the platform want one async substrate or is the split intentional), not something to silently "fix" inside a vendored file.
